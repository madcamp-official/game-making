# 1주 개발 로드맵

## 1. 결론: 무엇부터 만들 것인가

스프라이트를 먼저 대량으로 수집하거나 15개의 방을 먼저 만들지 않는다. 가장 먼저 아래의 **수직 프로토타입** 하나를 완성한다.

> 게임 시작 → 이상해씨 이동 → 적 1마리와 전투 → 적 처치 → 방 클리어 → 다음 방으로 이동

이 흐름이 실제 빌드에서 동작하면 같은 구조에 이벤트방, 상점방, 보스방과 나머지 층을 붙인다. 첫 프로토타입에는 이상해씨의 `Idle`, `Walk`, 기본 공격과 테스트용 적 하나만 사용한다.

## 2. 이번 주의 기술 방향

기간을 고려해 다음 기준으로 구현한다.

- 실시간 8방향 이동과 실시간 전투를 기본안으로 한다.
- 절차적 맵 생성은 하지 않고, 미리 제작한 방을 정해진 순서로 연결한다.
- 하나의 `Gameplay` 씬에서 방 프리팹을 교체하는 구조를 우선한다.
- 시스템을 먼저 완성한 뒤 같은 시스템에 콘텐츠를 추가한다.
- 포켓몬, 기술, 적, 유물의 수치는 가능하면 `ScriptableObject` 데이터로 분리한다.
- 첫날에는 플레이 가능한 회색 박스 맵을 사용한다. 최종 타일과 연출은 이후에 교체한다.
- 세이브, 다중 캐릭터, 복잡한 분기, 무한 던전은 이번 MVP에서 제외한다.

전투를 불가사의 던전과 동일한 격자 턴제로 만들고 싶다면 첫날 시작 전에 팀 전체가 결정해야 한다. 이동, 적 AI, 공격 처리 구조가 달라지므로 개발 중간에 실시간과 턴제를 전환하지 않는다.

## 3. MVP 완료 조건

아래 항목이 모두 동작하면 이번 프로젝트의 최소 완성본으로 본다.

- 시작 화면에서 한 판을 시작할 수 있다.
- 플레이어가 이동하고 공격하며 피해를 받는다.
- 적이 플레이어를 추적하고 공격하며 사망한다.
- 전투방의 적을 모두 처치하면 다음 방으로 이동할 수 있다.
- 각 층이 `전투 → 이벤트 → 전투 → 상점 → 보스` 순서로 진행된다.
- 1층, 2층, 3층을 차례로 진행할 수 있다.
- 보스는 각각 버터플, 코뿌리, 갸라도스다.
- 보스를 처치하면 이상해씨가 다음 단계로 진화한다.
- 이벤트 또는 상점에서 유물을 획득할 수 있다.
- 행복의알과 자뭉열매 효과가 동작한다.
- 플레이어 사망 시 게임 오버, 3층 보스 처치 시 게임 클리어가 표시된다.
- PC 실행 파일로 빌드해 처음부터 끝까지 플레이할 수 있다.

## 4. 구현 순서

### 단계 0 — 프로젝트 기준 고정

목표: 모든 팀원이 같은 환경에서 충돌 없이 작업할 수 있게 한다.

- Unity `6000.5.3f1` 사용
- Version Control Mode를 `Visible Meta Files`로 설정
- Asset Serialization Mode를 `Force Text`로 설정
- 기준 해상도와 입력 키 결정
- 실시간 전투인지 격자 턴제인지 최종 확정
- 폴더 구조 생성
- 테스트 빌드가 실행되는지 확인

완료 기준: 팀원 모두 저장소를 받아 Unity에서 오류 없이 열고 빈 테스트 빌드를 실행할 수 있다.

### 단계 1 — 한 개 전투방 수직 프로토타입

목표: 최종 그래픽 없이도 핵심 전투 반복을 검증한다.

- 벽과 바닥만 있는 테스트 방 제작
- 플레이어 이동, 충돌, 카메라 추적 구현
- 이상해씨 `Idle`, `Walk` 애니메이션 연결
- 기본 공격 1개 구현
- 공통 `Health`와 피격 처리 구현
- 테스트용 적 1종의 추적, 공격, 사망 구현
- 적이 모두 죽으면 출구 활성화
- 출구 진입 시 같은 테스트 방을 다시 로드

완료 기준: 에디터에서 시작해 적을 처치하고 출구를 통해 다음 방으로 넘어갈 수 있다.

### 단계 2 — 한 개 층 완성

목표: 1층의 처음부터 보스 처치와 진화까지 연결한다.

- `RoomFlowController`로 5개 방 순서 관리
- 이벤트방 상호작용 1개 구현
- 상점 UI와 구매 1개 구현
- 버터플 보스 구현
- 보스 처치 후 진화 연출과 능력치 변경 구현
- 방 사이에서 체력, 재화, 유물 유지

완료 기준: 1층의 다섯 방을 끊김 없이 진행하고 이상해풀로 진화한다.

### 단계 3 — 유물과 런 상태

목표: 한 판 동안 획득한 상태가 방과 층을 넘어 유지되게 한다.

- `RunManager`에 현재 층, 현재 방, 체력, 재화, 유물 기록
- `RelicData`와 유물 효과 적용 구조 구현
- 행복의알 구현
- 자뭉열매 구현
- 게임 오버와 재시작 구현

완료 기준: 유물 효과가 방 전환 이후에도 유지되며 새 게임을 시작하면 초기화된다.

### 단계 4 — 2층과 3층 콘텐츠 확장

목표: 검증된 1층 구조를 복제하지 않고 데이터와 프리팹 교체로 확장한다.

- 사막 방 세트와 코뿌리 보스 추가
- 바다 방 세트와 갸라도스 보스 추가
- 층별 일반 적과 난이도 곡선 설정
- 2층 및 3층 이벤트 구현
- 이상해꽃까지 진화 연결
- 3층 보스 처치 후 클리어 화면 연결

완료 기준: 새 게임부터 3층 클리어까지 한 번도 에디터 조작 없이 진행된다.

### 단계 5 — 밸런스, 연출, 빌드

목표: 기능 추가를 멈추고 제출 가능한 상태로 만든다.

- 한 판이 15~20분인지 측정
- 플레이어와 적의 체력, 피해량, 이동 속도 조정
- 피격 점멸, 넉백, 화면 흔들림, 사운드 추가
- UI 가독성과 조작 안내 개선
- 크레딧 화면 또는 크레딧 문서 연결
- 다른 PC에서 빌드 실행 테스트
- 치명적인 버그만 수정하고 기능 추가 중단

완료 기준: 팀원이 아닌 사람이 설명 없이 시작해 클리어 또는 게임 오버까지 플레이할 수 있다.

## 5. 권장 일정

| 시점 | 반드시 끝낼 일 | 시간이 남으면 |
|---|---|---|
| 1일차 | 프로젝트 기준 설정, 테스트 방, 이동, 카메라 | 이상해씨 걷기 애니메이션 |
| 2일차 | 공격, 체력, 적 AI, 방 클리어 | 피격 연출과 사운드 |
| 3일차 | 1층 방 흐름, 이벤트, 상점 | UI 스타일 정리 |
| 4일차 | 버터플 보스, 진화, 유물 구조 | 유물 추가 |
| 5일차 | 2·3층과 두 보스 연결 | 층별 고유 적 추가 |
| 6일차 | 전체 플레이테스트, 밸런스, 빌드 | 파티클과 화면 연출 |
| 제출 전 | 다른 PC 실행 확인, 크레딧 확인, 치명적 버그 수정 | 새 기능 추가 금지 |

일정이 밀리면 그래픽 종류와 적 종류를 줄인다. 방 이동, 보스, 진화, 게임 종료 흐름은 줄이지 않는다.

## 7. 주요 오브젝트와 역할

거대한 `PlayManager` 하나에 모든 기능을 넣지 않는다. 아래처럼 책임을 나누면 팀 작업과 테스트가 쉬워진다.

| 구성 요소 | 책임 |
|---|---|
| `GameManager` | 메인 메뉴, 플레이 중, 일시 정지, 게임 오버, 클리어 상태 전환 |
| `RunManager` | 현재 층·방, 플레이어 상태, 재화, 유물 등 한 판의 데이터 보관 |
| `RoomFlowController` | 방 순서, 현재 방 생성과 제거, 다음 방 이동 |
| `CombatRoomController` | 적 생성, 생존 적 확인, 방 클리어와 출구 활성화 |
| `PlayerController` | 이동 입력과 방향 처리 |
| `PlayerCombat` | 플레이어 공격, 쿨다운, 공격 판정 |
| `Health` | 피해, 회복, 사망 이벤트를 플레이어와 적이 공통 사용 |
| `EnemyController` | 추적, 공격, 행동 상태 전환 |
| `RelicManager` | 획득한 유물 등록과 효과 발동 |
| `UIManager` | 체력, 재화, 현재 층·방, 유물 UI 갱신 |

`GameManager`와 `RunManager`는 전역 오브젝트로 둘 수 있지만, 나머지는 가능하면 해당 씬이나 방 프리팹에 둔다.

## 8. 데이터 구조 권장안

반복되는 포켓몬과 유물은 코드에 수치를 직접 쓰지 않고 `ScriptableObject`로 만든다.

- `CharacterData`: 이름, 최대 체력, 이동 속도, 공격력, 스프라이트와 애니메이터
- `EnemyData`: 이름, 최대 체력, 이동 속도, 공격력, 행동 거리
- `RelicData`: 이름, 설명, 아이콘, 등급, 효과 식별자
- `RoomData`: 방 종류, 방 프리팹, 등장 적, 보상
- `FloorData`: 환경, 5개 방 순서, 일반 적 목록, 보스, 난이도 배율

처음부터 범용 데이터 시스템을 완벽하게 만들 필요는 없다. 1층이 완성된 시점에 중복되는 값만 데이터로 옮긴다.

## 9. 팀 병렬 작업 방식

단계 1의 수직 프로토타입까지는 핵심 규칙을 빠르게 합의한다. 이후에는 아래처럼 작업 영역을 나누는 것을 권장한다.

- 프로그래밍 A: 플레이어, 공격, 체력, 적 AI
- 프로그래밍 B: 방 흐름, 런 상태, 유물, 진화
- 콘텐츠: 맵·방 프리팹, 스프라이트 애니메이션, 보스 설정
- UI·연출: HUD, 상점, 이벤트, 게임 오버, 사운드와 이펙트

한 Scene이나 Prefab을 두 명이 동시에 수정하지 않는다. 공용 Scene에는 빈 배치 지점만 두고, 각 기능은 Prefab으로 만든 뒤 합친다.

## 10. Git 작업 규칙

- 작업 시작 전에 `main`을 최신 상태로 받는다.
- 기능별 브랜치를 사용한다. 예: `feature/player-movement`, `feature/room-flow`.
- 커밋에는 코드와 관련 `.meta` 파일을 함께 포함한다.
- `Library`, `Temp`, `Logs`, `UserSettings`는 올리지 않는다.
- Scene과 Prefab 담당자를 정하고 동시에 수정하지 않는다.
- 기능 하나가 플레이 가능한 단위가 되었을 때 작은 커밋을 만든다.
- 병합 전 Console 오류가 없고 테스트 Scene이 실행되는지 확인한다.

## 11. 지금 바로 할 일

1. 팀에서 실시간 전투 방식을 확정한다.
2. `Assets/Game` 폴더 구조를 만든다.
3. 회색 박스 전투방 하나를 만든다.
4. PMD Sprite Repository에서 이상해씨의 스프라이트와 `credits.txt`만 받는다.
5. 이상해씨 `Idle`과 `Walk`만 Unity에 임포트한다.
6. 플레이어 이동과 카메라 추적을 구현한다.
7. 캡슐이나 단색 Sprite를 테스트 적으로 놓고 공격·체력·사망을 구현한다.
8. 방 클리어와 출구 활성화까지 연결한다.

버터플, 코뿌리, 갸라도스와 나머지 에셋은 이 흐름이 성공한 뒤 받는다.
